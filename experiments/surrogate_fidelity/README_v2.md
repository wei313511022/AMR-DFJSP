# Evaluator fidelity v2 — full coverage, full candidate field, explicit tie handling

Supersedes `README.md` / `run_fidelity.py`, which measured 3 sizes × 30 instances × 12
rule-generated schedules. Three things changed, for three different reasons.

| | v1 (published Table IV) | v2 |
|---|---|---|
| sizes | n = 20/60/100 | n = 20/40/60/80/100 |
| instances | 30 per size | 100 per size |
| candidates | 12 rules | 12 rules + 6 policy cells + GA = **19** |
| rank statistic | γ, labelled τ_b | **τ_b**, with γ printed alongside |
| selection regret | first minimiser in list order | **expectation over the argmin set**, bracketed |

The instance pool is `test_case/v3/trend/full_{20,40,60,80,100}.jsonl`, m = 16 — the same
files and the same 100 instances per size the main benchmark reports, so Table IV is no
longer the one table in the paper on a reduced grid.

## Why 12 rules and not the full 60

The 60-combination grid is `../full_benchmark/results.csv`. Two facts about the 12, both
regenerated by `rule_selection.py` rather than asserted:

**They are the better half.** All 12 fall in ranks 3–30 of 60 by mean rank across the five
sizes; six are in the top 13.

**They span the batching spectrum**, which is the transport decision this problem turns on:
whether a robot fetches one parcel and returns, or accumulates a rack-full before
delivering. Measured as pickups per trip from the committed order — a maximal run from an
empty rack back to empty — so it is read off the schedule, no simulation.

The excluded half is `random`, `nearest_station` and `least_congested_station`. They are not
merely weaker: at n = 100 the worst combination executes several times the best. A candidate
that bad is ranked correctly by *every* evaluator, so including it raises τ for C̃ and Ψ̂
alike. It would inflate the headline rather than stress it — which is the opposite of what a
fidelity table is for.

## Why the policies and the GA

`README.md`'s own Known Limitation: v1's candidates came from rules that themselves plan
under Ψ̂, so Ψ̂ was ranking schedules it helped construct. The v10 factorial fixes this by
construction — cells **A** and **B** were trained to minimise C̃, **E** and **F** to
minimise Ψ̂, **C** and **D** against the executor. The field now contains schedules built to
exploit each evaluator under test, and `analyze_fidelity_v2.py`'s per-generator table
reports each evaluator's error on its own arm separately. The GA is a fourth, independent
generator: it optimises the collision-free decode.

Seed 44, greedy decode. Seed 44 is the only seed with all six cells finished at 4000 epochs
(`../full_benchmark/RESULTS_A-F.md`), so one seed keeps the six on a common footing; greedy
gives one deterministic schedule per cell. `best8` is not used here — it selects with Φ,
which is the ground truth this table is measuring against. Masks match training: A/C/E run
with L3 installed, B/D/F unmasked.

## Ties

Three places where an arbitrary convention was deciding a reported number.

1. **The rank statistic.** The published table's `τ_b` column is Goodman–Kruskal γ =
   (C−D)/(C+D), which drops tied pairs. It drops a *different* number for each evaluator —
   C̃ is integer-valued and ties often, Ψ̂ is continuous and almost never does — so the two
   columns were not computed on the same base. v2 reports τ_b (ties in the denominator) as
   the headline, with γ and both pair counts alongside.
2. **The selection regret.** `argmin_c C̃(c)` is a *set*. `min(g, key=…)` returns whichever
   member the candidate loop emitted first, so on a tied instance the number was a property
   of enumeration order. v2's headline is the mean over the minimiser set — what a uniformly
   random tie-break earns in expectation — bracketed by its best and worst members, with the
   old list-order value printed as `as-coded` so the two tables reconcile.
3. **Inversions.** Reported under both conventions: `inv_c` = D/(C+D) excludes tied pairs,
   `inv_a` = D/binom(k,2) counts every pair.

Executor-side ties need no convention: a pick counts as a hit when its *makespan* equals the
instance minimum, not when it is the same candidate.

## Reproduce

```
python run_fidelity_v2.py --workers 20      # ~13 CPU-hours, ~45 min on 20 cores; GA dominates
python analyze_fidelity_v2.py
python rule_selection.py
```

Outputs `fidelity_v2.jsonl` (one row per schedule), `fidelity_v2.csv`,
`fidelity_v2_summary.txt`, `rule_selection.txt`. v1's outputs are preserved in `archive_v1/`.
